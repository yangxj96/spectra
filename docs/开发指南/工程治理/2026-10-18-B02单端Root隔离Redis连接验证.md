# B02 单端 Root 隔离 Redis 连接验证

## 场景与调用方

本项补充 `DIAG-CORE-019` / `CHECK-CORE-019` 和 `IMP-BASE-003` 的单端连接故障场景。`CoreTwoProcessHttpTest` 启动两个不同 PID 的完整应用 JVM，使用专用 PostgreSQL 测试库与测试进程自启的随机端口、无持久化 Redis DB 5。第一应用通过本机随机端口 TCP 转发器连接隔离 Redis，第二应用直连同一 Redis。转发器可以关闭已有连接并拒绝新连接，仅影响第一应用；隔离 Redis 和第二应用保持运行。

测试创建随机合成的唯一 `ROLE_DEV_OPS` 用户。第一应用签发的 Access 在两端均可使用。隔离第一应用连接后，两端并发访问同一 Access：第一应用返回 503，第二应用继续返回 200；第一应用的停用写请求和密码登录均返回 503，第二应用拒绝停用最后有效 Root，返回 409 / `ROOT_EFFECTIVE_MINIMUM`。数据库中用户仍为 `ACTIVE`，有效 Root 人数为 1。恢复转发后，分别验证原 Access 在两端仍为 200，第一应用也恢复最后 Root 的 409 下限保护。这与 Redis 整体停启后的旧 Session 丢失不同：Redis 在单端隔离期间持续运行，因此原 Session 应保留。

本次只改测试夹具，不改生产协议或调用方代码。CodeGraph 与当前源码核对 Framework Session Redis 事实源、Core Root 有效计数及双 JVM 启动路径。Web 保持既有 `error_code` 和身份清理协议；OA/Workflow 的授权读取与后台入口仍需独立间接业务验收。

## 验收边界

本项模拟一个应用到安全 Redis 的 TCP 连接被切断并持续拒绝，而不是系统防火墙或真实跨主机网络故障。验证了失联实例的失败拒绝、未失联实例继续服务、连接恢复后的会话保留和最后 Root 下限；未覆盖 Redis 撤销与数据库提交之间的非原子窗口、初始化/策略故障恢复、OA/Workflow 间接业务及 B08 浏览器。八模块门禁不启用真实依赖测试且显式排除 `RegionServiceTest`；真实依赖证据来自独立定点命令。`CHECK-CORE-019` 和 B02 仍保持进行中。
