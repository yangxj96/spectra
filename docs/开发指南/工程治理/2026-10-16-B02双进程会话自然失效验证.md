# B02 双进程会话自然失效验证

## 范围与影响

本项补 `DIAG-BASE-005`、`IMP-BASE-003` 中 Access/Refresh 自然到期与会话策略跨进程读取的正式 HTTP 证据，并为 `BC-BASE-002` 的双进程边界提供局部验证。后端 CodeGraph 和当前源码确认，Framework 的签发、读取、轮换经安全 Redis Session/Refresh Hash，Core 的会话策略 Provider 每次从 PostgreSQL 读取；两个独立应用 JVM 没有共享进程内身份状态。Web CodeGraph 和源码确认 `AuthApi.refresh()` 通过现有请求客户端发送 Web Cookie，失败后 `refreshAccessToken()` 清理本地会话。OA/Workflow 共享认证边界，没有直接调用会话期限实现或策略写入。本项未改变端点、Cookie 或响应字段，因此没有改动 Web、OA、Workflow 源码。

测试在已有 `SessionTwoProcessHttpTest` 增加一个完整应用用例。两个 JVM 在同一专用 PostgreSQL 和 Redis DB 5 上运行，使用随机合成用户和授权快照。测试直接调整专用库的 Web Session 策略行，并在 `finally` 恢复原值、撤销合成用户 Session；这只用于验证两进程读取当前策略，不代表策略管理 HTTP 写入已由本项重新验证。

## 可观察行为

1. 首进程签发短时 Access、较长 Refresh；第二进程接受新 Access。Redis 中该 Access Session Key 自然到期后，两个进程的正式 HTTP 安全上下文均返回 401。
2. Access 已自然到期而 Refresh 尚有效时，第二进程通过正式 Web Cookie 与 CSRF HTTP Refresh 轮换；新 Access 可在首进程使用。
3. 专用库把会话绝对期限收紧到早于 Token Family 首次登录时间；两个进程均拒绝新 Access，首进程也拒绝对应 Refresh。轮换没有重置首次登录时间。
4. 恢复策略后再签发一组短时 Refresh；Redis Refresh Key 自然到期后，第二进程的正式 HTTP Refresh 返回 401。

## 仍未验证

用例使用合成身份与授权快照，并由测试直接调整专用库策略；它没有覆盖正式 Core 密码登录、角色变更、管理员策略 HTTP 写入或浏览器真实 Secure Cookie 发送。Access 自然到期后按用户/客户端/改密/踢旧撤销仍需各入口跨进程验证；Refresh 重放竞争、多实例会话配额、真实 Redis 停启恢复、旧格式会话上线处置、OA/Workflow 间接业务及 B08 浏览器身份失效仍在 B02 其余检查中。`BC-BASE-002` 与 B02 继续保持部分执行和进行中。
