# B02 有效 Root 隔离 Redis 故障恢复验证

## 场景与影响

本项补充 `DIAG-CORE-019` / `CHECK-CORE-019` 的真实安全 Redis 停启场景。`RedisFaultRecoveryHttpTest` 自启独立端口、无持久化的 Redis 子进程，正式应用通过 `spring.data.redis.url` 仅连接该子进程；PostgreSQL 使用 `devops00_spectra_db_test`，夹具只创建随机合成 Root。测试不停止共享 Redis，也不操作真实业务数据。

初始只有一个有效 `ROLE_DEV_OPS` 用户，其人数为 1，正式 HTTP 登录及上下文请求成功。停止隔离 Redis 后，旧 Access 的上下文请求、Root 密码登录和停用自身的写请求均返回 HTTP 503；数据库中的 Root 仍为 `ACTIVE` 且有效人数保持 1。重启为空的隔离 Redis 并等待运行态重新就绪后，重新登录成功；重启前的旧 Access 返回 401，新 Access 可用。唯一有效 Root 再尝试停用自身时返回 409 / `ROOT_EFFECTIVE_MINIMUM`，状态和人数不变。

CodeGraph 与当前源码核对了 Root 有效计数、`SecurityRedisExecutor`、Session 读取和 `DependencyReadinessProbe` 的调用链。探针故障退避最长 30 秒，正在执行的 Redis 命令还可能等待 10 秒超时，因此恢复轮询窗口从 30 秒扩至 90 秒。最初两次定点运行在 30 秒窗口内以 HTTP 503 超时；同一场景扩窗后通过，并非通过放宽故障拒绝断言。Web 的 `error_code` 契约未变；OA/Workflow 没有本测试直接调用，间接业务入口仍待验证。

## 验收边界

本项验证单应用进程中唯一有效 Root 面对安全 Redis 实际停机及重启时的 fail-closed、旧 Session 失效、重新登录和数据库 Root 下限保护。八模块门禁未启用真实依赖测试，并显式排除 `RegionServiceTest`；真实依赖证据来自前述定点与整组命令。两个应用进程同时经历 Redis 故障、Redis 撤销与数据库提交之间的非原子窗口、初始化/策略故障恢复，以及 OA/Workflow 间接业务入口仍未运行。`CHECK-CORE-019` 保持 `partially_executed`，B02 保持 `in_progress`。
