# B02 双实例 Root 隔离 Redis 故障恢复验证

## 场景与调用方

本项补充 `DIAG-CORE-019` / `CHECK-CORE-019` 与 `IMP-BASE-003` 的双应用故障场景。`CoreTwoProcessHttpTest` 启动两个不同 PID 的完整应用 JVM，共用专用 PostgreSQL 测试库和测试进程自启的随机端口、无持久化 Redis DB 5。第一应用通过命令行、第二应用通过进程环境变量指定同一隔离 Redis URL；测试仅停启这个子进程，不停止共享 Redis。

测试创建一个随机合成 `ROLE_DEV_OPS` 用户，初始有效 Root 人数为 1。第一应用签发的 Session 在两端均可访问。停止隔离 Redis 后，两端并发访问旧 Access 的上下文接口均返回 503；随后两端停用写请求和密码登录也均返回 503。数据库中的用户保持 `ACTIVE`，有效 Root 人数仍为 1。

同端口重启为空白 Redis 后，测试分别等待两个 JVM 的就绪探针恢复。旧 Access 与旧 Refresh 在两端均返回 401；第二应用重新签发的 Access 在两端均可用。两端尝试停用最后有效 Root 都返回 409 / `ROOT_EFFECTIVE_MINIMUM`，数据库状态和人数不变。测试验证的是共同 Redis 故障与恢复，不通过进程私有内存传递 Session。

CodeGraph 与当前源码核对了 `CoreTwoProcessHttpTest` 双 JVM 启动、Framework Session Redis 事实源、就绪探针及 Core Root 有效计数。Web 的请求与错误协议没有变化；OA/Workflow 没有直接调用这项 Root 写入口，目录与授权读取仍是未验证的间接影响。

## 验收边界

本项覆盖两个独立应用 JVM 共同经历同一个隔离 Redis 实际停机、重启及状态丢失后的认证、写入、Session 和 Root 下限行为。八模块门禁未启用真实依赖测试，并显式排除 `RegionServiceTest`；双进程真实依赖证据来自独立命令。未覆盖只有一端网络隔离、Redis 撤销与数据库提交之间的非原子窗口、初始化/策略故障恢复、OA/Workflow 间接业务或 B08 浏览器。`CHECK-CORE-019` 保持 `partially_executed`，B02 保持 `in_progress`。
