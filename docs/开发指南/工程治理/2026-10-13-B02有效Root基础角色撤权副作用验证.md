# B02 CORE-019 缺失基础角色时的 Root 撤权副作用验证

## 范围与调用方

2026-10-13 复核正式 `PUT /api/user/onboarding`：Web 的 `RoleAssignmentEditor` 经 `UserApi.submitUpdate` 发送 `removed_assignments`，Core `UserOnboardingServiceImpl.submit` 先调用 `UserService.modify`，再提交角色撤销。修改前，`modify` 在撤权之前自动补齐缺失的 `ROLE_USER`，`AuthorizationAssignmentChangeServiceSupport.ensureDefaultUserRole` 会立即撤销目标 Redis Session。若后续撤销最后有效 `ROLE_DEV_OPS` 被 Root 守卫拒绝，数据库补角色与安全版本虽回滚，已撤销的 Session 无法回滚。

当前源码和 CodeGraph 核对只有 `UserOnboardingServiceImpl` 调用 `UserService.modify`。用户创建和批量导入仍由 `UserService.create` / `createWithDefaultPasswordHash` 补齐基础角色；编辑路径现在在 `submitAuthorization` 成功后补齐，仍处于同一个数据库事务。OA/Workflow 没有直接调用用户编辑或撤权写入口，其公共身份、目录和授权读取是间接影响。本次没有改变 API 1.0.0 的请求和响应形状，Web 无需迁移。

## 合成场景与结果

`RootGovernanceFullHttpTest` 新增正式 Spring HTTP 用例，使用 Flyway schema、PostgreSQL `devops00_spectra_db_test`、Redis DB 5、随机合成部门/用户/授权和实际登录 Session。仅有一个有效 Root、且该用户缺少 `ROLE_USER` 时，用户编辑撤销其 `ROLE_DEV_OPS` 返回 409；Root 数仍为 1，原 Assignment 为 `ACTIVE`，`ROLE_USER` 未被写入，原 Access 仍返回 200。新增第二名缺少基础角色的 Root 后，撤销第二人的 Root 授权返回 200；其 Assignment 为 `REVOKED`、`ROLE_USER` 已补齐、旧 Access 返回 401，未受影响的操作者 Access 仍返回 200。既有同一测试类的停用和并发撤权用例继续通过，专项合计 3/3。

## 验证边界

本轮证明缺失基础角色时，最后 Root 撤权的已知提前 Session 撤销不再发生；没有把数据库事务与 Redis 操作声明为可原子回滚。若同一请求在授权撤销之后发生其他失败，已有即时 Session 撤销仍可能早于数据库回滚，这属于后续安全变更事务与外部副作用协调问题。身份、凭据、策略及初始化的正式 HTTP、双进程、自然失效、OA/Workflow 间接用例、Web 浏览器和独立 `error_code` 仍未完成。`CHECK-CORE-019` 维持部分执行，B02 维持 `in_progress`。
