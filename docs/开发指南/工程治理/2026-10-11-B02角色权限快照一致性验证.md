# B02 角色权限快照一致性专项验证（DIAG-CORE-032）

## 实现与影响

`RoleAuthorizationChangeServiceImpl.persist` 在角色版本 CAS、角色 Permission/GrantablePermission 重建后，同一事务内清理该角色所有未逻辑删除 Assignment 中不再被角色声明的 Access/Grant Boundary，并清理不再被任何边界引用的 Scope 与规则。清理失败会使角色变更事务回滚；事务外调用清理器会被拒绝。已撤销 Assignment 的旧边界也被清理，之后角色重新扩权不会恢复旧授权。

`AuthorizationAssignmentChangeServiceSupport.apply` 在检查目标角色和 Boundary 前对 Role 行加 `FOR SHARE` 锁，与 Role Authorization Apply 的版本更新锁串行化。先写入的 Assignment 会被随后的角色收缩清理；角色收缩先完成时，Assignment Apply 只能读取新权限并拒绝旧能力。

2026-10-12 正式 HTTP 验证发现 Role Apply 原先对 `sec_role_permission` 与 `sec_role_grantable_permission` 全量软删除后直接插入仍保留的唯一键，实际 PostgreSQL 会因 `(role_id, permission_id)` 唯一约束拒绝提交。现以固定 SQL 在角色 CAS 事务内软删除旧关系，并用 `ON CONFLICT` 恢复仍声明的原行；保留审计与版本字段，权限/可授予权限的删减仍由 Boundary Reconciler 在同一事务内完成。并发失败的 Role version 冲突映射为 HTTP 409，调用方可重新预览。

后端 CodeGraph、现行源码及 Web CodeGraph 复核：Core 的登录快照加载、授权预览与应用、部门重组和通知受众复用这一授权状态；OA/Workflow 通过公共安全上下文及权限检查间接受影响，没有直接调用角色变更服务。Web 的角色、Assignment 与授权方案页面读取既有授权端点；接口请求/响应形状和版本均未修改，因此本项无 Web 协议改动。OA/Workflow 在全后端门禁中编译并通过静态检查。
