# B02 受控发送与角色定义缩权竞争验证

## 范围

本项补 `DIAG-CORE-034`、`IMP-CORE-007`、`CHECK-CORE-034` 中 BUSINESS 角色定义缩权与受控发送 Apply 同时竞争的证据。CodeGraph 和源码核对：`RoleAuthorizationChangeService.apply` 在同库事务中更新 Role Permission、清理失效 Assignment Boundary、推进受影响用户安全版本并撤销 Session；受控发送 Apply 在同库事务中锁操作人用户行后读取当前权限快照。通知管理 Web 页经 Core `1.0.0` Preview/Apply API；OA、Workflow 后台使用公共通知端口，不直接调用该受控发送 Service。

## 真实依赖测试

环境为原生 Windows PowerShell、mise `test`、JDK 25 和仓库 Maven Wrapper；使用专用 PostgreSQL `devops00_spectra_db_test`、Redis DB 5，以及随机合成 BUSINESS 角色、操作人、通知受众和请求。没有读取本机凭据或使用真实业务数据。

测试先给合成 BUSINESS 角色授予 `notification:send:preview/apply` 和 `user:read` 有效范围，目标用户经正式 HTTP 登录并生成可用的受控发送 Preview。授权操作者再经正式 Role Authorization Preview 获得令牌，在独立事务中调用公开 `RoleAuthorizationChangeService.apply` 移除 `notification:send:apply`；变更完成后暂缓提交。目标用户另一线程直接调用受控发送 Apply，在缩权事务提交前等待；提交后因当前权限失效拒绝。角色版本和目标用户安全版本均递增，Role Permission 已删除，通知 Preview 仍未消费，对应 Request 为零；旧 Access 返回 401，重新登录的授权快照不含 Apply 权限。

## 验收边界

本项验证单 JVM 双线程中“角色缩权写入并持锁在前、受控发送 Apply 在后”的提交顺序，使用正式角色变更 Service 和专用库事务。它尚未验证 Apply 先持锁的反向顺序、两个应用 JVM 同时竞争该角色变更、真实跨主机网络或其他 OA/Workflow/Quartz 故障。`CHECK-CORE-034` 与 B02 仍保持进行中。
