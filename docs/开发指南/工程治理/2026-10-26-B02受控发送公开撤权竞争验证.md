# B02 受控发送与公开 Assignment 撤权竞争验证

## 范围

本项补 `DIAG-CORE-034`、`IMP-CORE-007`、`CHECK-CORE-034` 中“真实撤权路径与 Apply 并发”的证据。CodeGraph 与源码核对：公开 `AuthorizationAssignmentChangeService.revoke` 经审计 Service 进入同库事务，锁目标 `sys_user`，更新 Assignment、推进安全版本并撤销 Session；受控发送 Apply 在事务中先锁同一用户行，再检查权限快照与入队。Web 受控发送页只经 Core Controller 的 `1.0.0` Preview/Apply API，OA、Workflow 后台使用公共通知端口，不调用该受控发送 Service。

## 真实依赖测试

环境为原生 Windows PowerShell、mise `test`、JDK 25 和仓库 Maven Wrapper；使用专用 PostgreSQL `devops00_spectra_db_test`、Redis DB 5 与随机合成用户、Preview、通知请求。没有读取本机凭据或使用真实业务数据。

正式应用测试建立两个有效 Root，使撤销目标 Root 时仍满足最后有效 Root 下限。备份 Root 在独立事务中调用公开 `AuthorizationAssignmentChangeService.revoke`；Service 完成写入后，测试让事务暂缓提交。另一线程以目标用户直接调用受控发送 Apply，确认它在撤权事务提交前等待；提交后因当前权限失效被拒。数据库中目标 Assignment 为 `REVOKED`，Preview 仍为 `PREVIEWED`，对应通知请求数为零；目标用户原 HTTP Session 也不能再次 Apply。原有正式 HTTP 输入拒绝、成功发送、同进程并发及双 JVM 唯一消费同时复跑。

## 验收边界

本项调用正式公开 Service 和真实事务，但测试为单应用进程中的两个线程，撤权由合成 Root 安全上下文发起；没有调用角色定义整体缩权的 Preview/Apply，也没有在两个 JVM 或真实跨主机条件下竞争撤权。`CHECK-CORE-034` 的其他 OA/Workflow/Quartz 故障竞争仍未完成，B02 继续 `in_progress`。
