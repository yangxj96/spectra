# B02 CORE-023 绑定验证码尝试预算验证

## 范围与实现

- `AuthenticationController` 在绑定码发送时将当前已认证用户 ID 传给 Core 用例。短信和邮箱绑定码在现有用途＋地址 Redis 键中保存用户 ID 与验证码 HMAC 摘要；绑定核验必须同时匹配用户、地址和验证码。登录验证码仍走原有独立路径。
- `SecurityVerificationCodeStore.consumeWithinAttemptBudget` 由 Framework 的 Redis Lua 脚本实现：在一个原子操作中确认验证码及 TTL、先核对发起用户，再增加该用户的尝试计数和比较验证码；其他用户不能耗尽当前码。成功或达到配置的 `verificationCodeMaxAttempts` 时删除验证码及计数。缺少 TTL、绑定值损坏、Redis 命令失败、脚本结果未知或回复丢失均拒绝，不把未知结果当作不存在。
- 绑定码发送与核验分别命中 10 分钟 5 次和 15 次的用户＋来源 IP 外层限流；该过滤器位于 Token 认证之后。通知重新发送采用每次生成的短幂等标识，`ntf_request.business_id` 与 `idempotency_key` 均保持在当前字段长度内；通知入队失败只按当前摘要清理，避免删除并发产生的新码。
- 管理员清理绑定验证码时，`clear_attempts=true` 同时清理对应尝试计数。无效或耗尽的验证码按通用验证码错误处理；Redis 故障继续拒绝。

## 调用方与影响

CodeGraph 和当前源码核对了 `VerificationCodeService`、`AuthenticationIdentityBindingServiceImpl`、Common 验证码端口、Framework Redis 实现、限流过滤器、缓存管理，以及 Web 个人资料绑定和运维缓存维护入口。Web 仍调用原有 `/api/security/authentication/bind/sms|email`、`/api/security/identities/phone|email`，请求体不变；无需改 Web 协议。OA 和 Workflow 没有绑定码直接调用，完整后端门禁覆盖了其编译与静态检查。`IMP-CORE-005` 的其他任务、用户导入、诊断、Quartz 与双进程场景不由本项推定通过。
