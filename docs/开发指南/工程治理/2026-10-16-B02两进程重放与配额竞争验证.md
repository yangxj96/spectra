# B02 两进程重放、配额与到期后撤销验证

## 范围与影响

本项为 `BC-BASE-001` 补齐两个独立应用进程上的 Refresh 重放围栏与多实例 `max_sessions` 证据，并为 `BC-BASE-002` 补齐"Access 已自然到期但 Refresh 仍有效"时按用户和排除令牌撤销入口的跨进程拒绝证据。后端 CodeGraph 与源码确认：Refresh 一次性消费、Family 围栏、会话名额预留/提交都只依赖共享安全 Redis，不依赖进程内状态；两个应用 JVM 各持自己的 Spring 上下文与 Redis 连接池，但读写同一 Redis DB 5。

测试在既有 `SessionTwoProcessHttpTest` 增加四个完整应用用例，并新增仅在 `spectra.test.session-http=true` 下装载的测试夹具 `SyntheticSessionController`（只存在于测试类路径，用于在第二个进程上驱动一次新的会话签发）。该控制器映射为 `/security/test/session/issue`，需要有效认证身份才能到达，不影响生产端点、Cookie 或响应字段，因此未改动生产源码、Web、OA 或 Workflow。

## 可观察行为

1. **跨进程重放围栏**：在首进程签发 Web 会话，在第二进程用同一 Refresh Cookie 完成轮换；随后在首进程重放旧 Refresh 返回 401，且轮换产生的新 Access 在两个进程都返回 401，新 Refresh 也返回 401——重放即撤销整个 Token Family。
2. **并发消费只成功一次**：同一 Refresh 同时发往两个进程，至多一个返回 200；若某进程返回 200，其新 Access 随后在两个进程都被拒绝，原 Refresh 也被拒绝。任意交错下都不存在可用的新 Access。
3. **多实例共享配额**：Web 策略设为 `REJECT_NEW` 且 `max_sessions=1` 时，首进程签发一个会话后，第二进程通过合成签发入口再开会话返回 **409**（`已达到该账号的最大并发会话数`）；共享 Redis 的 `USER_TOKENS` 集合仍只有 1 个成员，首会话在两端保持有效。对照组（默认策略）第二进程签发入口返回 200，证明入口可用而非 404。
4. **Access 到期后按用户/排除令牌撤销**：把 Web `access_ttl_seconds` 收紧到 3 秒签发两个会话，Access Redis Key 自然到期后两端均 401（Refresh 仍有效）。首进程调用 `revokeUserSessionsExceptToken(userId, keptAccess)` 后，被排除会话仍能在第二进程用 Refresh 轮换（200），另一会话的 Refresh 在第二进程返回 401；随后首进程 `revokeUserSessions(userId)`，被排除会话轮换出的新 Refresh 在第二进程的刷新返回 401。

## 仍未验证

用例使用合成身份与授权快照，并由测试直接调整专用库 Web 策略；未覆盖正式 Core 登录、角色事务、管理员策略 HTTP 写入或浏览器 Secure Cookie。真实 Redis 停启恢复、旧格式会话上线处置、Access 自然到期后按客户端/句柄/改密/踢旧的跨进程撤销、角色变更跨进程，以及 OA/Workflow 间接业务仍在 B02 其余检查中。`BC-BASE-001` 的两个子项已具备两进程证据；`BC-BASE-002` 的按用户与排除令牌入口已有 Access 到期后两进程证据，其余入口及整体仍保持部分执行和进行中。
