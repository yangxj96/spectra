# B02 角色快照跨部门与业务入口验收（CHECK-CORE-032）

## 范围与依据

本次沿用 `DIAG-CORE-032` 已实施的角色缩权同事务 Boundary 清理、角色行共享锁、Session 撤销和重新登录快照。CodeGraph 与当前源码核对了角色授权 Apply、部门合并/拆分、通知受众目录、OA 通讯录和 Workflow 流程定义入口。角色变更没有 OA/Workflow 的直接调用方；这两个模块通过公共安全上下文及权限检查间接受影响。部门重组则改变 Core 部门成员、组织闭包及活动授权范围中的部门规则，通知受众按现行目录重新展开。

新增 `RoleAuthorizationFullHttpTest.departmentMergeAndRoleShrinkReachAudienceOaAndWorkflow`，仅在 `spectra.test.real-deps=true`、`DB_URL` 指向 `devops00_spectra_db_test` 且 `REDIS_DB=5` 时运行。测试使用随机合成用户、角色、部门和行政区划；通过正式 Flyway 应用、PostgreSQL、Redis、Core HTTP、OA HTTP、Workflow HTTP 及通知受众目录执行，不使用业务数据。

## 行为核对

1. 合并前，目标用户登录后可读取 OA 通讯录与 Workflow 流程定义；原部门和角色受众均解析到目标用户。OA 通讯录的 Assignment 使用 `RULES` 部门范围，能够核对授权规则重映射。
2. 部门合并 Preview/Apply 成功，组织版本增加一次，活动授权部门规则从源部门重映射到新部门，目标用户旧 Access 被撤销；重新登录后两个业务读取仍成功，新部门受众解析到目标用户。相同 Apply 再次提交不能成功，组织版本不再增加。
3. 将目标用户从合并部门拆分到新部门后，组织版本再增加一次，旧 Access 再次失效；重新登录后 OA/Workflow 读取成功。通知受众由合并部门转到新部门，源部门不再包含该用户。
4. 将目标角色缩减为仅保留 `role:read` 后，OA/Workflow 旧 Access 均返回 401；重新登录后两个入口均返回 403，上下文不再含 `oa:contact:read` 和 `workflow:process:read`。角色受众仍能按有效 Assignment 解析目标用户，证明权限缩减没有把有效角色关系误删。

既有 `RoleAuthorizationFullHttpTest` 还覆盖并发角色 Apply 只有一个成功、另一个 409，失效 Access/Grant Boundary 与孤立 Scope 清理、同主机两个独立 JVM 的跨进程旧 Access 拒绝及重登录快照收缩；合成 PostgreSQL 专项覆盖事务回滚和角色行锁竞争。以上证据共同用于 CHECK-CORE-032，不把本次单 JVM 合并/拆分用例解释为跨主机竞争或 OA/Workflow 全部业务验收。
