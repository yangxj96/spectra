# B02 身份解绑的有效 Root 与会话验证

## 范围与调用链

本项补验 `CHECK-CORE-019` 的身份解绑入口。当前调用链为 Web 个人资料 `ProfileBinding` → `AuthenticationIdentityApi.unbind` → `DELETE /api/security/identities/{id}` → Core `AuthenticationIdentityBindingServiceImpl.unbind` → 身份撤销、Root 策略行锁与人数复核、Redis 用户 Session 撤销。Framework Access/Refresh 校验通过 `DatabaseSecurityUserLoader` 从数据库重新加载当前用户。OA/Workflow 没有身份解绑的直接调用，仍通过公共身份和授权上下文间接受影响。按工作区与子项目 CodeGraph 查询定义和调用方，再以当前源码 `rg` 复核；Core 两处索引定位的源码已变化，以当前文件为准。

原入口先读取身份列表、后进入下层 Root 行锁。普通用户同时解绑两个身份可能都读到旧列表，最终留下零个身份。仅剩一个身份时抛通用异常，HTTP 不是稳定的冲突码。成功解绑未撤销已签发的用户 Session。另一次正式 HTTP 测试发现：有效 Root 计数认可本地 EMAIL/SMS 身份，但 Access/Refresh 的数据库重载只查 PASSWORD 身份；移除密码身份后，仍被计为有效的 Root 实际返回 401。

影响图复核：`IMP-BASE-003` 的公共 Redis 撤销端口和 Web 失效处理是本项直接路径；`IMP-CORE-001` 的 Root 与身份服务是直接路径，OA/Workflow 通过安全上下文间接受影响。`IMP-CORE-007` 的角色快照、Quartz 和通知后台身份没有新增写调用，用户重载仍沿用同一 Assembler 与快照端口；本项只证明身份变化后的单进程 Access 重载，不能代替角色跨进程或后台任务验收。`IMP-BASE-001` 的审计清洗器及错误响应字段没有改动；此前审计专项仍有效，本项没有新增正式审计表或 OA/Workflow 审计消费测试。

现在解绑先取得 Root 策略行锁，再读取活动身份；最后身份冲突返回 HTTP 409。成功撤销后经公共端口撤销用户的 Redis Session。重载用户从活动 LOCAL PASSWORD、EMAIL、SMS 身份中选取可用身份，沿用现有凭证年龄、账号状态及授权快照组装检查。Web 在成功解绑后立即清理本地会话并跳转登录；冲突或请求失败时保留会话。API 路径和请求体未改变。

## 验证边界

身份解绑目前是单应用进程、正式 PostgreSQL/Redis 的成功、失败与并发 HTTP 证据；Redis 命令失败后的数据库回滚、两个应用进程共同处理解绑、自然失效，以及身份以外的凭证、策略、初始化入口尚未在本项运行。Redis 撤销位于数据库事务内但不能与数据库提交原子化；若后续事务步骤或提交失败，已撤销的 Session 不能恢复。Web 静态门禁通过，不等于浏览器交互验收；全库 Prettier 的 7 个既有格式差异仍阻断 Web 完整格式门禁。`CHECK-CORE-019` 与 B02 继续保持部分执行和 `in_progress`，不据此推定整个周期验收。
